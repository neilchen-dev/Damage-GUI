# Phase 2.1 — Unified Prediction Traceability

Implemented on `qt-redesign`, preserving existing algorithms, OOD logic, schema, and the workbench layout.

1. **Files.** Updated `qt/panels/prediction.py`, `qt/workflow.py`, `qt/main_window.py`, `qt/task_adapter.py`, `qt/widgets/activity_panel.py`, `qt/panels/history.py`, `qt/panels/batch.py`, `qt/i18n.py`, `storage/repositories.py`, and the existing Qt test's database isolation. Added `scripts/capture_qt_prediction_traceability.py`, `tests/test_qt_prediction_traceability.py`, and this report.
2. **Lifecycle.** Single Prediction now runs through TaskManager rather than a separate QThread. The business task kind and stored job kind are `prediction`. The presentation immediately inserts PENDING; the worker records PENDING/RUNNING, calls the existing PredictionService with captured bundle/condition/config, and returns to TaskManager. Qt waits for terminal persistence reconciliation before publishing SUCCESS/FAILED/CANCELLED to Activity and ending the inspector's running state. Very fast jobs may traverse intermediate states between paints.
3. **Persistence.** Each submission gets its own UUID, even for repeated identical inputs. `jobs.details_json` stores level/h/v/deg, confidence derived from the existing OOD report, and calculation duration. `prediction_results` stores the existing scalar result fields: condition, level, peak_intensity, damage_area_ratio, ood_level/distance, truth metrics where available, and duration_ms. No field matrix is written to SQLite. Job duration includes worker execution/persistence; result duration is PredictionService calculation time. TaskManager owns the terminal state, including a late cancellation. Cancellation does not interrupt the algorithm; it is checked at service boundaries.
4. **Repositories.** Reused JobRepository and PredictionResultRepository's existing insertion/read APIs. Model upsert now uses ON CONFLICT UPDATE rather than replacement, preserving a known artifact_path when another frontend upserts metadata without a path. This avoids destroying model provenance during Batch recording. Job history ordering is now `created_at DESC, id DESC`; filters and pagination remain SQL-level. No migration was added.
5. **History/Activity.** Prediction and Batch share the same session table, capped at 100 recent rows, and the same persistent History filters. Prediction list input shows h/v/θ/level. Details display timestamps, status/error, condition, scalar metrics, OOD confidence/distance, model type/software/hash and artifact availability. Model files are not loaded to display history. Results supports both the single-prediction text summary and existing Batch output table. Double-clicking either job type opens persistent details.
6. **Restore Inputs.** Restores level/h/v/deg without executing or loading a model. Running work prevents restoration. A restored level that differs from the currently loaded model requires loading a matching model before prediction, so the UI cannot silently predict with a different level. Historical field matrices are not restored.
7. **DB failure.** A calculation can succeed while tracing fails. Its field/inspector still render; the bottom status and result summary explicitly report history persistence failure in Chinese/English, and existing logs receive ERROR records. The warning survives language switching. Job/result/model write failures are checked; they do not become fake algorithm failures. A failed PredictionService yields a FAILED job with a bounded error summary; traceback stays in application logs.
8. **Compatibility.** The unchanged schema accepts previous databases. Acceptance tests load nullable legacy jobs, metadata-free model results, and existing Batch rows; missing metadata or model files show an explanatory message. No result matrix/model file is required to inspect context. CLI/Web/Tk continue using the same service and repositories. Batch still uses its existing service/runner and passes the prior end-to-end tests. Prediction and Batch are mutually exclusive at the Qt controller boundary to avoid concurrently invoking a shared model.
9. **Performance.** See `outputs/qt_phase21/evidence.json`: mixed history first pages measured with 1,000 and 10,000 prediction jobs, each limited to 1,000 Qt model records. Equal timestamps and SQL pagination are tested without overlap. Twenty real repeated predictions are measured including UI delivery/rendering; this is not algorithm throughput. Single-prediction adapter polling temporarily uses 16 ms to keep completion responsive; Batch retains its existing callback/coalescing behavior. Repository I/O stays off the UI thread. Finalizer tasks return no matrices, preventing completed internal tasks from retaining every past prediction field.
10. **Evidence.** Nine screenshots under `outputs/qt_phase21`: success with Activity, HIGH/LOW history, detail, restore inputs, mixed history, Chinese detail, and Chinese/English persistence failure. `traceability.sqlite` is retained alongside the screenshots and contains the actual synthetic acceptance jobs/results/models. The script directly verifies foreign_key_check, status/model/input references, and exact PredictionService scalar outputs.
11. **Tests.** Full regression suite: 244 passed, 1 skipped. New headless acceptance covers real RBF HIGH (3/100/10) and LOW (2/150/20), 20 distinct jobs, result/model/metric persistence, failure summary, cooperative cancellation, metadata-free bundles, old nullable jobs, missing files, restore, filters, mixed stable pagination, session cap, DB degradation, and Batch regression. Existing Qt tests use isolated test databases so regression runs do not write to a user's normal history.
12. **Limits.** The existing models.app_version describes model software provenance; no independent execution-version field exists. Persistence uses existing short transactions; an abrupt process crash between result recording and terminal update can leave a nonterminal job requiring later recovery. Explicit DB failure is visibly degraded and cannot guarantee complete history. No historical field matrix is restored, model artifacts are not automatically loaded, and cross-platform native shell opening has not been manually exercised outside macOS. History result detail remains capped at the existing first 1,000 rows. The previous valid plot remains available behind the error state after a failed prediction, as in the established workbench behavior.
13. **Phase 2.2 proposal.** Add interrupted-job reconciliation on startup and pagination/export for persisted result rows. Consider atomic job/result completion in a shared repository operation, and an explicit model-artifact selection action for restored inputs; avoid expanding workspace scope.

Reproduce:

QT_QPA_PLATFORM=offscreen .venv/bin/python scripts/capture_qt_prediction_traceability.py
.venv/bin/python -m pytest -q
