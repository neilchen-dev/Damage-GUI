# Phase 2.0 — Batch Workflow & Traceability

Implemented on `qt-redesign`. Existing batch algorithms, TaskManager, and SQLite schema are unchanged.

1. **Files.** New `qt/workflow.py`, `qt/panels/batch.py`, `qt/panels/history.py`, `qt/log_bridge.py`, `scripts/capture_qt_batch_workflow.py`, and `tests/test_qt_batch_workflow.py`. Updated `qt/main_window.py`, `qt/task_adapter.py`, `qt/widgets/activity_panel.py`, `qt/theme.py`, `storage/repositories.py`, and the existing Qt navigation regression expectations.
2. **Batch architecture.** `BatchWorkspace` owns the dark summary/preview and a separate light inspector. `Workflow` connects presentation signals to `BatchService`. The parser remains authoritative: required `h/v/deg`, optional `job_id/level`, supported levels F/M/P. Schema-invalid rows remain visible and executable as runner-generated failed outcomes; file-level errors prevent submission. Error summary shows at most ten rows. CSV preview contains at most 100 records.
3. **TaskManager.** CSV parsing, batch execution, DB reads/writes, and final state reconciliation run through the existing manager and Qt adapter. No runner or repository operation runs directly on the UI thread. Activity shows session jobs, while History independently reads persisted jobs.
4. **Progress/cancel.** Existing runner callbacks report the completed count before each next row. The wrapper reports the final processed count. Qt coalesces progress events per poll; the 5 px bar avoids excessive repainting. Cancellation requests the existing cooperative flag, retains completed outcomes and CSV, and reconciles SQLite with the TaskManager terminal state, including late cancellation. The adapter handles the manager's pre-start cancellation path without introducing another status. Closing the window waits for active work to finish its cancellation/persistence path.
5. **SQLite/repositories.** The same ModelRepository, JobRepository, and PredictionResultRepository own persistence. Added parameterized model lookup, filtered/paginated job listing, and bounded result-row reads. No schema migration was added. PENDING → RUNNING → terminal transitions share the same job ID passed to the batch runner. Database failures remain logged and calculations/output continue; the summary warns when tracing is unavailable.
6. **History.** All/Prediction/Batch and status filters apply inside repository queries before pagination. A page contains at most 1,000 jobs, with previous/next controls. Selecting a record loads job timestamps, paths, status, error, metadata, and up to 1,000 persisted result rows. Double-clicking a session batch job opens its History detail. Tables use QAbstractTableModel, sorting, row selection, resizable columns, and 30 px rows.
7. **Traceability.** `prediction_results.job_id → jobs.id → jobs.model_id → models.id` exposes app_version, training_data_hash, type, level, samples, and commit. CSV preserves the existing output columns, including row_job_id (CSV job_id), model_id/model_version, OOD, metrics, timing, and error. SQLite row IDs disambiguate duplicate CSV job IDs. The submitted bundle remains captured even if the UI loads another model. Output paths are added to existing details_json and already stored with result rows. Outputs are reserved using exclusive creation and suffixes; an existing file, including the source CSV, is never overwritten.
8. **Performance.** See `outputs/qt_phase20/evidence.json`: validation plus event-loop delivery measured with synthetic CSVs of 100, 1,000 and 10,000 rows. Only 100 preview records enter the Qt model. These are local offscreen wall-clock measurements, not a runner throughput benchmark.
9. **Screenshots.** Twelve real rendered screenshots under `outputs/qt_phase20/`: empty, validated, running, completed, row errors, expanded Jobs, Results, History list/detail, and cancellation. English 1440×900 and Chinese 1280×720 key states are included. All predictions use `tests/synthetic_data.py`; no private data or fabricated metrics.
10. **Tests.** Full suite: 243 passed, 1 skipped. The workflow regression checks real success/output/repository linkage, model switching, invalid rows, level mismatch, preserved existing output, fatal output failure, cooperative cancellation, history selection, metadata, restart persistence, and CSV preview sizes. It also verifies database failure leaves output usable and shows a traceability warning. Existing CLI/Web/Tk/algorithm/numerical and Qt regressions remain in the full suite.
11. **Limits.** Legacy bundles without metadata cannot supply model/hash provenance. The software version shown is the stored model app_version; no independent execution-version column exists. Input files can later change or disappear; the current schema stores paths rather than an immutable source snapshot. History detail previews the first 1,000 stored results; complete results remain in the CSV. Opening a folder uses QDesktopServices and opens the containing directory rather than selecting a specific file. Qt's existing single-prediction execution remains separate; this phase persists Batch jobs, and the Prediction history filter reads existing persisted prediction jobs. Cross-platform file launching was implemented through Qt, but this run exercised macOS offscreen, not native Windows/Linux desktops. Logs stream existing application records while the window is open; they do not load an earlier log file tail.
12. **Next phase.** Extend the same controller/persistence path to single predictions, add result pagination/export from History, and consider immutable input snapshots if stronger long-term audit guarantees are required.

.venv/bin/python -m pytest -q
