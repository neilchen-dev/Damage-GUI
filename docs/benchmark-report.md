# 性能基准报告（Benchmark）

日期：2026-09-02 ｜ 版本：2.1.0 ｜ 数据来源：本机 `dist/data`（F/M/P 各 120 工况）

**追溯**：种子 42，commit `b6803e2`。数字摘自 `examples/results/benchmark/benchmark_{level}.{md,csv,json}`。

> **口径（务必先读）**
> - **Mean/Median/P95(ms) 是"每张图"的推理耗时**，不是每批。批量模式下 = 批总时 / 批大小。
> - **Thr(/s)** = 每秒可产出的毁伤场张数 = `batch / (mean_ms × batch / 1000)`。
> - **cold** = 进程内首次推理（含懒加载/预热），batch=1；**warm** = 预热后稳态，batch=10/100/1000。
> - **PeakMem(MB)** 是 **Python `tracemalloc` 峰值**（仅 Python 层分配），**不是进程 RSS**，
>   不含 BLAS/原生库在 C 层的常驻；用于同机横向比较，不可当作部署内存上限。
> - **Artifact(B)** = 落盘模型产物字节数；**Load(s)** = 从磁盘加载模型耗时。
> - **单机单次测量**，未做多机/多次重复统计；数值用于**同机横向比较与量级判断**，
>   不是可跨硬件迁移的绝对 SLA。

## 4. 关键发现

1. **产物体积：pod_rbf 最小，是 rbf 的 ~1/9、nn/linear 的 ~1/35。**
   pod_rbf **2,500,805 B（2.5MB）** vs rbf 22,388,758 B（22.4MB）、nn 85,981,532 B（86MB）、
   linear 91,935,608 B（92MB）。POD 降维把每工况的高维场压到 K=20 模态系数，这是它
   最主要的工程收益，也是选它做交付模型的核心理由之一（可随 GUI/Web 一起分发）。
2. **推理延迟：生产模型 pod_rbf 单图 ~8–12ms，满足交互式 GUI/Web 实时预览。**
   warm batch=100 每张图 F 10.16ms / M 11.97ms / P 9.29ms；cold 单图 F 8.43ms /
   M 12.27ms / P 9.58ms。对"改一个 h/v/deg 立刻重算一张 473×473 场"的交互场景绰绰有余。
3. **纯速度上 nn/linear 远快于 pod_rbf/rbf**（linear warm 低至 0.18–0.53ms/图，
   nn ~0.9–1.9ms/图，吞吐最高 5671/s），但：① 它们产物巨大（86–92MB）；② linear/nn
   是"查表/最近邻"式预测，**精度与质心定位不如 pod_rbf**（见消融报告 §3），且 nn 在
   P 级 R² 仅 0.1159。**速度快不等于可交付**——本项目要的是"连续参数化 + 定位准 + 产物小"。
4. **批量对 pod_rbf/rbf 的每张图耗时基本无改善**（F pod_rbf：cold1 8.43 → warm1000 9.83ms），
   说明其瓶颈在单场重建的稠密计算而非批处理调度；线性基线则随批量显著摊薄
   （linear F：cold1 0.88 → warm10 0.18ms）。若未来有"海量离线批量出图"需求，
   这是 pod_rbf 的一个已知性能特征（非缺陷），可据实评估。
5. **内存（tracemalloc 峰值）四模型都在 344–355MB 同一量级**，pod_rbf 略低（347–348MB）。
   再次强调这是 Python 层峰值口径，不含原生 BLAS 常驻，仅用于同机横比。
6. **训练耗时 pod_rbf 与 rbf 同量级（~130–250s/级）**，benchmark 内 pod_rbf 的 Train(s)
   （F 162.8 / M 204 / P 170.6）与消融 design 套件一致；离线训练，非交互路径，可接受。
